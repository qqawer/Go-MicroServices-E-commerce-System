# 库存扣减、返库与订单消息修复（2026-09-22）

## 原问题与本批改动

对照 [mxshop 库存实现](https://github.com/iceymoss/mxshop/blob/58142016702831ed31a62b9ece431c935a24ba04/mxshop_srvs/inventory_srv/handler/inventory.go) 与 [订单实现](https://github.com/iceymoss/mxshop/blob/58142016702831ed31a62b9ece431c935a24ba04/mxshop_srvs/order_srv/handler/order.go)。本仓原实现沿用了未检查提交、直接按请求返库、循环内更新返库状态、查询错误被当成消费成功等问题。

原始隔离 MySQL 测试实际复现：同一订单返库两次，库存 98→100→102；包含两个商品的返库返回重试；数据库查询报错却确认消息。本批修复如下：

| 原问题 | 现在的行为 |
| --- | --- |
| Reback 不检查订单流水，重复调用重复加库存 | 根据原扣减快照返库；同一订单仅归还一次；请求可带清单作一致性校验，不能用它覆盖原数量 |
| 多商品返库在循环中反复改订单状态 | 所有商品归还和一次状态变化在同一事务里提交 |
| Sell 依赖未初始化 Redis 锁，失败分支泄漏事务/锁 | 使用 MySQL 唯一订单行串行处理同订单请求，按商品 ID 排序进行条件扣减；移除库存服务未使用的 Redis 锁字段 |
| Save/Commit 错误忽略、读写使用不同事务 | 检查所有数据库错误；商品变更与流水在同一事务；只在提交成功后报告成功 |
| MQ 查询失败仍确认、批次只处理第一条 | AutoReback 复用 Reback；任一条未完成返回重试，已处理条目重投不会重复归还；完整批次成功才确认 |
| 取消早于扣减时没有记录，晚到请求仍扣库存 | 没有扣减记录也保存 CANCELLED；晚到 Sell 明确拒绝 |

## RPC 契约

- `Sell(SellInfo)`：订单号为 1–200 位字母/数字/下划线/连字符；商品清单 1–1000 项，ID 和数量为正 int32。重复商品合并数量、检查溢出后按 ID 排序。相同订单、相同规范化清单重复调用成功且不再扣减；更换清单返回 AlreadyExists；已返库/取消订单返回 FailedPrecondition。
- `Reback(SellInfo)`：订单号必填，商品清单可省略。已扣减订单按保存的快照加回库存，已归还/取消不再增加数量。提供的清单不匹配时拒绝。库存缺失、溢出或写入失败会使整笔返库回滚。
- `GetStockOperation(StockOperationRequest)`：新增按订单号查询已提交处理结果的方法，返回订单号、状态与扣减快照。两仓三份协议/生成代码一致。
- 原 InitInv、SetInv、InvDetail 保留既有职责；创建商品初始化不会被本批重复改造。

`stockselldetail` 继续使用原表，状态 1=RESERVED（已扣减）、2=RELEASED（已归还），新增 3=CANCELLED（未扣减就取消）。状态 0 只在数据库事务内部用于认领，正常提交不保留 0。

查询 NotFound 只表示当前没有已提交的流水，不能证明没有进行中的 Sell。需要取消时调用 Reback，让取消决定与 Sell 竞争同一订单行；即使取消先完成，晚到的扣减也无法绕过它。

缺货导致整个 Sell 回滚，包括这次新建的流水；相同订单在尚未取消时可以补货后再尝试。库存数量已发生变化的成功订单按现有流水判断，不重新扣减。接口没有新增请求头，使用业务里已有的订单号。

## 订单与消息衔接

- `order_srv/handler/order.go`：Sell 返回错误后先保存取消决定，再提交返库事务消息。没有根据 RPC 的 err 推断库存未扣减。订单数据库提交结果未知时，重新读取持久决定，避免误退成功订单库存。
- `order_srv/handler/transaction.go`：事务回查依据 `order_transaction`。正在创建或尚未执行的消息被回查取消时，写入取消决定；后续创建订单必须锁定同一决定行，已取消不能重新提交。数据库不可用返回 Unknown，不猜测最终结果。
- 订单及订单明细、购物车已结算项、COMMITTED 决定和超时事件在同一事务提交。订单号改为 UUID，并添加订单号唯一约束。
- 超时关闭订单与 `order_event` 返库事件在同一事务提交，提交之后才尝试发消息。发送失败事件仍待发送；`DispatchOrderEvents` 可重新读取并发送。MQ 已接收但确认丢失时可能重复投递，由库存幂等承受。
- 超时消费遍历整个批次，已支付订单跳过；状态更新不能把关闭订单恢复成已支付。支付渠道验签、查单/关单和晚到支付补偿仍属于支付批次，不能仅靠本地状态保证真实支付竞争安全。

### 新表与运行边界

`0003_inventory_transactions.sql` 扩展原 stockselldetail：订单号主键与精确比较、JSON 明细、状态约束；新增两张订单表：

1. `order_transaction`：PREPARING(0)、COMMITTED(1)、CANCELLED(2)，供创建与回查共同判断。迁移将已有订单登记为创建已提交。
2. `order_event`：业务事务中写入的待发送事件，同一订单/主题唯一；发送确认后标记 published。

本节记录上一批 04 的边界：当时没有启用 MQ 运行时，CreateOrder 保留未就绪拦截。最新接入见 [订单创建与运行时](../order_srv/CREATION.md)。当时启动流程没有挂载生产者/消费者和定时 dispatcher。`DispatchOrderEvents` 是可测试、可复用的恢复入口，服务重启不会凭这个函数定义自动运行。下一批 05 需要统一启动/关闭 MQ、持续调度待发送事件、恢复长期未完成的订单决定、补齐前端请求幂等与持久商品快照，并通过真实 Broker 故障测试后再开放创建订单。

## 验证与迁移

- 真实 MySQL + gRPC：三轮各 1000 个不同订单、100 并发争抢 100 件库存，均恰好成功 100 次、最终 0；同订单并发扣减 100 次只扣一次；重复返库消息 1000 次只归还一次。
- 多商品缺货/第二件写入故障整笔回滚；同订单不同清单拒绝；提前取消与并发取消；扣减提交后响应丢失可以查询和重试。
- 真正提交后人为丢失提交响应，以及提交前失败：验证库存、订单和关闭事件的持久结果。SQL 使用真实 MySQL，MQ 使用发送替身，未发送真实业务消息。
- 原三条复现、整批消息处理、未知结果回查、延迟执行取消、关闭失败不发送返库、发送失败换 dispatcher 恢复、晚到支付不能覆盖关闭状态均加入回归。
- `bash ci/check.sh`、`python3 tests/integration/run.py`；三份库存协议使用固定 protoc 工具生成，两仓 `scripts/generate-goods-proto.sh` 可重复生成。

生产升级继续使用 `deploy/scripts/migrate-business.py check/up`。预检拒绝无效订单号、重复订单、损坏或非法库存快照；迁移前生成私有备份，保留既有库存数量和有效流水。旧 0001/0002 校验和不变。本批新增 0003，总业务表数为 15。
