# 商品查询基线：2026-09-24

第 07 批的第一步已完成：建立可复现的端到端基线。生产业务查询、索引和连接池没有改动，尚无优化提升百分比。

在这台 Mac 的隔离测试环境中，10 万商品、100 次/秒混合请求、三轮各 120 秒，共 **36,002 次业务成功请求，0 错误，0 dropped iterations**。三轮 P95 为 **17.28 / 21.64 / 15.63 ms**，中位数 **17.28 ms**。这是指定负载下的本机结果，不是 AWS 容量，也不是最大或长期稳定容量。

## 环境和方法

- Apple M4，10 个逻辑 CPU，16 GiB 内存；macOS 15.3 arm64。Docker VM 为 10 CPU / 7.653 GiB，共享主机，另有 6 个原有容器运行；未停止它们。
- Go 1.25.6，Python 3.14.6，k6 v2.3.0。MySQL 8.0.46；缓冲池 128 MiB，max_connections 151，现有迁移 0001–0005。测试 MySQL 未设置单独 CPU/内存配额。
- RPC 基于 `d74d9e4f354bf01d42943970dd9f28385064c58c`，Web 基于 `07258979319b53ac47d7e86bf5029feff04195ed`。新增的测试入口及驱动以 JSON 证据中的源码 SHA256 固定；本轮没有修改生产源码。
- 链路为主机 k6 → 主机真实 HTTP 路由 → 主机真实 TCP gRPC → Docker MySQL。复用生产 handler、关联读取、Info 日志和默认 DB 连接池。测试入口跳过 Nacos/Consul，采用 loopback 端口与只读保护；Web 为 Gin release。不是 mock 或直接数据库压测。
- 固定 seed `20260924`，1 万/10 万商品、20 品牌、50 末级分类（共 62 个分类节点），每商品一条库存记录；随机品牌/分类/价格，图片仅返回地址不下载。详情轮换 1,024 个固定分散样本；列表与筛选使用固定查询。
- 每档数据先混合预热 30 秒；单接口和升压档位每轮探索 30 秒。10 万商品的 100 RPS 确认重复 3 次，每次先预热 30 秒再测 120 秒。混合比例为详情 50%、首页列表 30%、品牌+价格筛选 20%。预分配/最大 VU 均为 100，它不等于 100 个同时在途请求。
- 业务成功需同时满足 HTTP、JSON、准确总数/分页长度、合法不重复商品 ID、关联数据及筛选条件；详情还核对指定商品字段。错误 JSON/错误数据不计成功。
- 阈值在测前固定：P95≤300ms、P99≤1000ms、业务错误率≤0.1%、丢迭代为0。确认三轮均通过。

## 已定位的成本与下一步

普通商品列表在 `goods_srv/handler/goods.go` 先做精确 COUNT，再取一页数据，并批量 Preload 品牌和分类。日志实测：详情每请求 3 条 SQL，普通列表/筛选 4 条，一级分类场景 5 条；关联加载是批量查询，不是每件商品单独查两次。

| 普通首页列表计数 | 1万商品 | 10万商品 |
| --- | ---: | ---: |
| 计数调用数 | 601 | 601 |
| 累计扫描行 | 6010000 | 60100000 |
| 每次计数扫描行 | 10000 | 100000 |
| MySQL计数平均耗时 ms | 3.24 | 13.89 |

两档 `EXPLAIN ANALYZE` 均显示 `WHERE deleted_at IS NULL` 的 COUNT 使用商品表全表扫描；10万商品单次诊断扫描100,000行，实际计数约19.4ms。第一页主查询只读取20行；品牌筛选已有品牌索引，10万数据的计数先读取品牌1的4,916行，再筛到2,257行。因此下一项优先试验 **保留准确total，改善计数的索引访问**，而不是先上缓存或把品牌Preload删掉。该证据说明可优化的成本，尚不能证明它是系统吞吐上限的唯一瓶颈。

建议后续单独提交索引试验：核对覆盖 `deleted_at` 的索引是否被优化器采用，比较普通列表及写入成本，保留品牌/价格查询的结果语义；不要修改已应用的0001–0005。然后用同样数据、日志、参数和至少三轮复测判断收益。索引候选仍未实施，未给出提升比例。MySQL官方说明可参考 [EXPLAIN ANALYZE](https://dev.mysql.com/doc/refman/8.0/en/explain.html)。

## 资源、时间和统计边界

- 确认阶段采样到的进程 RSS 峰值（MiB）：goods-rpc 23.6, goods-web 41.5, k6 527.6；MySQL Docker CPU采样峰值 122.57%（Docker口径，100%约一个CPU）。这不是排除了采样空隙的绝对峰值。
- `ps pcpu` 是历史口径；累计CPU time、RSS、Docker累积I/O留在原始资源记录中。没有数据库锁等待/活跃连接的完整时序或CPU/heap profile，不能据此排除连接池或主机竞争。
- QPS按业务成功数除以计划注入时长；可能包括最多10秒宽限期内结束的请求，不是按最后响应时间计算的完成窗口吞吐。延迟为k6请求发送+等待+接收时间，不含初始DNS/建连或客户端JSON断言；定义见 [k6指标文档](https://grafana.com/docs/k6/latest/using-k6/metrics/reference/)。
- GORM父级Find日志包含Preload时间，不能把父子trace时间相加。MySQL digest对部分预处理语句覆盖不完整，故完整SQL次数取生产日志，计数扫描行取覆盖到的PFS digest，计划另看EXPLAIN。
- 两次前期运行不计入本报告：一轮为补齐SQL统计而中止；另一轮出现约12分钟UTC中断、monotonic未同步变化，疑似主机暂停。最终轮使用仅在任务内生效的caffeinate，并逐轮验证UTC/monotonic差值和响应时间戳跨度，30轮全部通过。原始异常记录保留但不混入统计。
